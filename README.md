# 三角协作 ｜人类决策、AI 分工、独立验收

**Triad Collaboration** · 版本 0.2.0

这个仓库把一套三人分工写成可以直接使用的文件：人定目标，C 规划并独立验收，W 执行并报告。附一个项目级技能，以及一个能在本机自动派发任务、收取报告、接着派下一轮的通道。

## 这套东西为什么存在

出发点是给额度紧张的 Plus 用户省主力模型的额度：规划和验收留在主力模型上，执行交给当前能用的免费 agent，派工、交报告、返工由通道接起来，人只在方向、取舍和最终验收上出现。

这是初衷，不是效果结论。仓库里没有额度计量，也没有跨任务的对比数据；C 的派工、读报告、审阅和返工沟通仍然消耗主力额度，省多少取决于任务本身。免费能力随平台和账号当时可用额度变化，不保证某个 agent 长期可用，也不承诺永久免费。

仓库名、技能目录名与调用名统一为 `triad-collaboration`；L-C-W 是角色缩写（L 决策、C 规划与检查、W 执行），不是另一个项目名。

## 三个角色

| 角色 | 职责 | 一轮结束时的状态 |
| --- | --- | --- |
| L · Leader | 你。定目标、范围、取舍，做最终验收 | 依据实际结果接受，或提出修正 |
| C · Coordinator | 规划、写任务单、派工、独立检查实际成果 | 给出有证据的审阅结论 |
| W · Worker | 按任务单执行，交出成果、检查证据和未完成项 | 固定本轮报告，等待审阅 |

C 用你日常的主力 AI，它要判断、要写标准、要挑毛病；W 用你当前能用的免费 Agent，它只按单执行。这是分工建议，不是对某个平台的推荐。

本实践当前用 Codex 作 C、WorkBuddy 作 W。角色协议可以搬到别的工具，但各工具的技能识别、文件访问和派工能力要单独确认。

## 一轮的闭环

1. **L 提需求**：要什么结果、在哪个目录、什么算做完。
2. **C 写任务单**：唯一请求ID、允许改哪些文件、交付物位置、逐条验收标准、时间预算。
3. **C 派工**：配好通道时，任务单由通道送到 W 的执行目录；没配时 C 输出可转发的任务单，由 L 传递。
4. **W 执行并交固定报告**：改了什么、怎么检查的、实际结果、异常、未验证项、下一步。
5. **报告回到 C，C 自己核对**：打开实际成果逐条比对验收标准，区分“已验证 / 未通过 / 未验证”。审阅是 C 的动作，通道只负责把任务单和报告送到位、记下回执。
6. **不通过就开新一轮**：旧报告保留不覆盖；通过后交 L 最终验收。

W 报告完成不等于验收通过。C 不拿报告当结论，L 也不被跳过。

## 审阅分三层

1. **初审**：C 逐条对照验收标准，指出具体位置、影响和复查方法，并给出下一轮要求。
2. **W 修订后复审**：C 重新打开实际成果核对，不因为 W 写了“已修正”就放行。
3. **交付或发布前复核**：关键标准重走一遍，隐私与对外内容单独过一遍。

本轮没有真实改动就写“无需改动”，不虚构工作量；每个结论都要有对应的实际动作和证据。L 已就某个具体操作给出授权时，不必为同一件事反复索要确认。

## 分工不重叠

- C 不因为 W 暂时不可用就顺手把该 W 交付的成果做完，再声称经过了独立复核。正确降级是继续规划与诊断、如实报告阻塞，由 L 决定是等 W 还是改分工。
- W 不替 C 判定通过，也不替 L 最终验收。
- 只有在 L 明确同意改变分工时，C 才可以直接执行，并注明“C 直接执行”，同时失去独立检查者身份。

这是本项目的分工约定，不扩写为对所有平台的硬性限制。

## 0.2.0 的状态与验证范围

自动通道随本仓库提供。维护者在自己的 Windows 机器和 WorkBuddy 5.9.3 上，用它跑完了一个无害的两轮案例：第一轮故意留下缺项，C 读实际 JSON 后判 `needs_revision`；第二轮修正，C 独立核对后 `accepted`，两轮都核对了原生运行记录里的实际模型。这份公开包是那次验证之后的脱敏整理。

验证范围到这台机器、这个版本、这一个案例为止。其它机器、其它版本、复杂业务、空闲唤醒没有随公开包验证过，因此不承诺跨版本兼容，也不承诺无人值守长期运行。

通道把本机已有的两段原生能力参数化：按 `workbuddy-5.9.3` 的 `automations` 表结构写一条 ACTIVE 的一次性任务定义，结构不符就拒绝；报告事件按配置里的协作根目录存放。它不读 token，不改 WorkBuddy 目录权限，不写 sessions 和运行记录，不设登录启动项。空闲唤醒属于维护者本机的另一套机制，没有随包提供；公开的是 C 保持在线直接派工这一种模式。

## 入门

从 [QUICKSTART.md](QUICKSTART.md) 开始。自动模式要先备好三个目录（通道仓库、业务项目根、私有配置与备份区）、两个自己跑过的参考任务，再执行一次 `init`。人工模式只要两个独立会话，不需要安装任何东西。

第一轮建议挑容易核对的活，比如把三条自己写的待办整理成一页清单。只给允许处理的资料。

## 现有能力与限制

现在能做的是：角色协议、任务单与报告格式、独立检查清单、人工传递步骤、一个能在支持项目级技能的客户端里加载的技能（含模板），以及在明确边界内可用的自动通道。

还不能做的：不会自己登录执行器、创建会话或读取远端成果；没有经过陌生用户实测，也没有跨客户端、跨设备的长期验证；不保证在任何 AI 客户端都能被发现并自动加载；省额度效果没有定量对比数据。

这套流程不授予新的工具、账号或发布权限。发布、发信、上线这类外部操作，仍按你已有的授权和实际工具要求执行。

## 让这套方法起作用的约定

报告是检查的起点，不是结论，C 必须看到实际交付物。L 保留最终决策：需求或范围有实质变化时回到 L，例行执行不必反复请示。每轮用轮次号、请求ID和具体文件锚定，报告固定之后，修正写进新一轮。长任务建议单轮 30 至 45 分钟，接近上限就存下成果、未完成项和下一步，不无限重试。模型按难度与成本配置，记录实际依据，不把“请求的型号”当成“实际使用的型号”。投递结果不确定时，先用同一个请求ID查状态，不换 ID 盲目重投。
