# 三角协作 ｜人类决策、AI 分工、独立验收

**Triad Collaboration** · 人决定目标，C 规划并独立验收，W 执行并报告。这是一个把该分工写成可复制文件的模板仓库，附一个项目级技能，由 **SL-9ithub** 整理。

仓库名、技能目录名与调用名统一为 `triad-collaboration`；L-C-W 是角色缩写（L 决策、C 规划与检查、W 执行），不是另一个项目名。

## 为什么做这个

**让 Plus 的额度花在规划和把关上，把执行交给免费 Agent。**

三角协作面向额度紧张的 Plus 用户：人类决定方向，主力 AI 负责规划与独立验收，可用的免费 Agent 承担执行。目标是让派工、报告回收、检查与返工这几步自动流转，不必由人来回搬运内容。

这个思路基于一个朴素判断：规划与验收要判断力，执行耗时长。把能交给免费 Agent 的长活分出去，主力额度集中到需要判断的部分；不过派工、读报告与审阅仍发生在主力侧，总量是否更省要按实际任务看。

两点必须说清，否则容易变成空头承诺：

- **免费能力随平台和账号当时可用额度变化。** 本项目不保证某个免费 Agent 长期可用，也不保证它在你的账号上一定有额度。选 W 时用你当前确实能用的那一个。
- **省多少额度还没有定量对比结果。** 本项目没有做过跨账号、跨任务的额度计量，也不抄任何具体订阅限额。想估算自己的情况，用你自己账号的现有额度实测。

## 首版做到哪一步

v0.1 提供三样东西：一个可复制的项目级技能、四类协作模板、一份能照着跑完的教程。

- **配好可用且获授权的连接后**，C 应当直接协调 W：派工、收报告、检查都在同一条链上走，你不用中转。
- **本包不含通用自动连接器。** 未配连接时按教程人工传递任务单与报告，闭环照样成立，代价是你要在两个会话之间搬内容。

自动流转是目标，人工闭环是当前可用的底线。这两句话不冲突，但不该混着说：现在能用的是后者，前者要等你自己的连接就位。

## 三个角色

| 角色 | 职责 | 一轮结束时的状态 |
| --- | --- | --- |
| L · Leader | 你。定目标、范围、取舍，做最终验收 | 依据实际结果接受，或提出修正 |
| C · Coordinator | 规划、写任务单、派工、独立检查实际成果 | 给出有证据的审阅结论 |
| W · Worker | 按任务单执行，交出成果、检查证据和未完成项 | 固定本轮报告，等待审阅 |

**C 与 W 怎么选**：C 用你日常的主力 AI，因为它要判断、要写标准、要挑毛病；W 用你当前可用的免费 Agent，因为它只按单执行。这是分工建议，不是对某个平台的推荐——你手上哪个能用就用哪个。

本实践当前用 Codex 作 C、WorkBuddy 作 W。角色协议可以搬到别的工具，但各工具的技能识别、文件访问和派工能力要单独确认。

## 一轮的闭环

1. **L 提需求**：要什么结果、在哪个目录、什么算做完。
2. **C 写任务单**：唯一请求ID、允许改哪些文件、交付物位置、逐条验收标准、时间预算。
3. **C 派工**：有已授权连接就直接派给 W；没有就输出可转发的任务单，由 L 传递。
4. **W 执行并交固定报告**：改了什么、怎么检查的、实际结果、异常、未验证项、下一步。
5. **C 独立检查实际成果**：自己打开或运行，逐条对照验收标准，区分“已验证 / 未通过 / 未验证”。
6. **不通过就开新一轮**：旧报告保留不覆盖；通过后交 L 最终验收。

关键点：**W 报告完成不等于验收通过**。C 不拿报告当结论，L 不被跳过。

## 审阅不是一次就结束

一次初审能发现明显问题，但不能代替复查。本项目的约定是：

1. **初审定位问题**：C 逐条对照验收标准，指出具体位置、影响和复查方法，并给出下一轮要求。
2. **修订后复审**：W 改完，C 重新打开实际成果核对，不能只读 W 的“已修正”。
3. **交付或发布前再复核**：关键标准重走一遍，隐私与对外内容单独过一遍。

三条纪律：

- **没有真实改动就不写“已优化”。** 若本轮无需改动，就写“无需改动”，不要虚构一轮工作量。
- **不靠固定次数放行。** 不是“检查两次就算过”，而是每次检查都要有对应的实际动作和证据。第二次检查可以重点看成果一致性、完整性，以及上一轮问题是否真的修掉。
- **不绕过 L 的最终决策。** 但 L 已经就某个具体操作给出授权时，不要为同一件事反复索要确认。

## 分工不重叠

C 负责规划、诊断与独立检查，W 负责实际生产成果，两者不互相代做：

- C 不会因为 W 暂时不可用就顺手把该 W 交付的成果做完，再声称经过了独立复核。正确降级是：继续规划与诊断，如实报告阻塞，由 L 决定是等 W 还是改分工。
- W 不会替 C 判定通过，也不会替 L 最终验收。
- 只有在 L 明确同意改变分工时，C 才可以直接执行，并必须标注“C 直接执行”，同时失去独立检查者身份。

这是本项目的分工约定，不扩写为对所有平台的硬性限制。

## 入门概览

完整步骤见 [QUICKSTART.md](QUICKSTART.md)，这里只给骨架：

1. **取得文件**：在仓库页点 *Use this template* 生成自己的项目，或[下载 main 分支源码压缩包](https://github.com/SL-9ithub/triad-collaboration/archive/refs/heads/main.zip)解压。已有项目只想借技能时，把 `.agents/skills/triad-collaboration/` 整个文件夹复制到该项目的 `.agents/skills/` 下即可，模板跟着技能一起走。
2. **加载技能**：在项目里启动 C 的会话，显式调用 `$triad-collaboration`。客户端不支持技能时，把角色规则直接写进会话，走人工模式。
3. **开两个会话**：一个 C 会话、一个独立 W 会话，把[启动语](prompts/start-cn.md)分别发进去。
4. **跑一轮**：C 出任务单 → L 转给 W → W 交报告和成果 → L 转回 C → C 独立检查。
5. **看结论**：C 给出“已验证 / 未通过 / 未验证”，L 打开实际成果决定是否验收。

第一轮建议挑容易核对的活，比如把三条自己写的待办整理成一页清单。只给你允许处理的资料。

## 现有能力与限制

**能做**：提供角色协议、任务单与报告格式、独立检查清单、人工传递步骤，以及一个可被支持项目级技能的客户端加载的技能（含模板）。

**还不能做**：本包不含通用自动连接器，不会自己登录任何执行器、创建会话、传文件或读取远端成果；没有经过陌生用户实测，也没有跨客户端、跨设备的长期验证；不保证在任何 AI 客户端都能被发现并自动加载。省额度效果没有定量对比数据。

**边界**：这套流程不授予新的工具、账号或发布权限。外部操作（发布、发信、上线）仍按你已有的授权和实际工具要求执行。

## 让这套方法起作用的约定

- **报告是检查的起点，不是结论。** C 必须看到实际交付物。
- **L 保留最终决策。** 需求或范围有实质变化时回到 L；例行执行不必反复请示，已授权的具体操作不重复索要确认。
- **每轮可定位。** 用轮次、请求ID和具体文件锚定一轮工作；报告固定后，修正写进新一轮。
- **长任务能续接。** 建议单轮以 30 至 45 分钟为目标，接近上限就保存成果、未完成项和下一步，不无限重试。
- **模型可配置。** 按任务难度与成本选择执行模型，记录实际依据；不把“请求的型号”当作“实际使用的型号”。
- **投递有不确定就先查。** 同一个请求ID先查状态，不换ID盲目重投。
