# 教学案例：一页待办清单（全篇为模拟）

**以下全部是虚构的教学模拟文案，不是真实执行记录、不是测试结果，也不含任何人的项目材料。** 其中的请求ID、目录、日期都是教学用的示例值。你可以用同样的输入自己跑一遍，然后保存自己的真实证据。

三条设计约束，先说清楚：

1. **全篇模拟。** 没有任何一段来自真实会话，也不能当作“某软件确实支持某操作”的证据。
2. **需求从第一段起就只要求能由文件正文核对的条件。** 这一版的需求是重新设计的模拟需求，不是把某位真实用户的要求改松，也没有中途把标准换成更容易的替代品。
3. **保留一处真实会发生的失误**：W 漏了一个复选框，还在报告里声称全部满足；C 靠逐行读文件才发现。

## 1. L 提出需求

> 新建 `deliverables/todo.md`，把三件事整理成一页清单：整理书桌（2026-03-07）、归还图书（2026-03-08）、备份照片（2026-03-08）。每项一行，用标准 Markdown 复选框，行末写 `截止：YYYY-MM-DD`，按日期从早到晚排。只创建这一个文件，不联网、不装依赖。
>
> 验收只读文件正文，四条：① 三条待办的名称与两个日期与上面一致（只核对名称和日期，允许复选框、`截止` 标签与分隔符这类附加符号，不因它们判为不一致）；② 按日期升序，03-07 排在 03-08 前面；③ 每行都以 `- [ ] ` 开头；④ 只含一行标题 `# 待办清单` 与三条待办，可有空行，无额外解释。

注意这条需求的形态：四条都能靠**打开文件、看字符**判定，不需要点击界面、不需要特定软件。这不是简化标准，而是在提需求阶段就把“可核对”作为条件本身。

## 2. C 第01轮任务单

- 请求ID：`demo-round-01`（教学示例编号）。
- 目标：`deliverables/todo.md` 一页待办清单。
- 可改范围：仅新建 `deliverables/todo.md`。
- 验收：直接采用 L 的四条，编号与文字不变。
  - ① 逐行比对三条待办的名称与两个日期，附加符号不算差异。
  - ② 读三行的先后顺序。
  - ③ 逐行看行首前缀，数出 3 个 `- [ ] `。
  - ④ 通读全文，确认除标题、三条待办和空行之外没有别的内容。
- 明确写死一条：**四条都能由文件正文判定，不得改成“看起来像复选框”“格式大致正确”之类的近似说法。**
- 回报：实际检查、真实结果、未验证项，附交付正文。
- 传递：人工模式，L 把任务单交给 W。

## 3. W 第01轮交付与报告

> 对应 `demo-round-01`。已按顺序写出三项，①②③④ 全部满足。等待 C 审阅。

```markdown
# 待办清单

- [ ] 整理书桌 — 截止：2026-03-07
- 归还图书 — 截止：2026-03-08
- [ ] 备份照片 — 截止：2026-03-08
```

## 4. C 独立检查并退回

> 我逐行读了交付正文，不是看 W 的结论：
>
> - ① 三条的名称与两个日期一致 —— 通过。
> - ② 03-07 在 03-08 前面 —— 通过。
> - ③ 第二行是 `- 归还图书 — …`，**行首没有 `[ ]`，未通过**。
> - ④ 全文只有一行标题、三条待办和空行 —— 通过。
>
> 第01轮判定：**需修正**。另外注意：W 报告写的是“①②③④ 全部满足”，与文件实际不符——**报告不能当作结论**，这就是必须自己打开文件的原因。

第02轮任务单：请求ID `demo-round-02`，范围仍只有 `deliverables/todo.md`。给“归还图书”那一行补上 `- [ ] ` 前缀，其余字符一个不动；四条验收标准原样保留。新建第02轮报告，第01轮报告保留不覆盖。

```markdown
- [ ] 整理书桌 — 截止：2026-03-07
- [ ] 归还图书 — 截止：2026-03-08
- [ ] 备份照片 — 截止：2026-03-08
```

> 对应 `demo-round-02`。只补了第二行前缀，其余内容未改。逐行核对：三条名称与日期一致、07 在 08 前、行首 `- [ ] ` 共 3 个、全文只有一行标题加三条待办（另有空行）。四条我都读文件确认过。

## 6. C 第02轮审阅

> 我重新打开文件逐行核对：① 三条名称与日期一致，通过；② 顺序正确，通过；③ 三个 `- [ ] ` 都在行首，通过；④ 无多余内容（空行不算），通过。
>
> 给 L 的结论：四条全部**已验证**，本轮检查通过。我的检查只覆盖文件正文，不涉及任何界面行为；是否接受由你最终决定。

## 7. L 最终验收

> 我把 `deliverables/todo.md` 的正文自己读了一遍，四项都符合我最初提的要求，本次接受。

这个案例展示三件事：

1. **W 的报告会写错**，所以 C 必须打开文件看实际内容，而不是抄 W 的结论。
2. **标准一次定死，中途不放宽。** 本例的四条从一开始就只要求读正文，所以不存在“做不到就改标准”的空间。如果真遇到 C 读不到的条件，正确做法是记“未验证”并交回 L，而不是换一条更容易的。
3. **L 的验收是具体动作**：自己读一遍正文并确认，这一步不能由任何人代签。

实际使用时，每条“我已检查”都要对应一次真实操作。本案例的结论不能当证据，它只是演示检查该长什么样。
