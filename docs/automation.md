# 自动派工与人工传递

这套流程有两种跑法：自动通道让 C 直接派单、收报告、审阅、确认并接续下一轮；人工传递由 L 在中间转发。两种模式的角色分工完全一样，区别只在于谁搬文件。

## 自动模式做什么

`tools/triad_bridge` 把本机已有的两段能力参数化后公开：

| 原能力 | 公开形式 | 变化 |
| --- | --- | --- |
| 原生一次性派工（写一条 `automations` 定义） | `plan` / `submit` / `status` | 作者机器常量 → 私有配置 |
| 报告事件（publish / wait / ack） | `publish` / `wait` / `ack` | 项目根 → 配置里的 `cooperation_root` |
| 备份目录 ACL 收紧 | `submit` 内部前置步骤 | 机制不变，仍用 pywin32 加回读校验 |

它按 `workbuddy-5.9.3` 的 `automations` 表结构写一条 ACTIVE 的一次性任务定义，其余什么都不写：不改 sessions、不写运行记录、不读 token、不动 WorkBuddy 目录权限、不设登录启动项。表结构、账号绑定、路径、报告摘要任何一项对不上，就停手报错，没有强制绕过的开关。

配置前要先把三类目录分开：完整通道仓库、业务项目根（`cooperation_root`）、私有配置与备份区。业务项目必须是业务项目根的直接子目录，且三处不能互相嵌套；具体要求与可复制的建目录命令见 [auto-setup.md](auto-setup.md) 第 0 节。

C 保持在线时走完这一圈：

```text
submit(第 N 轮) → wait(55s 一轮) → 读报告、核对 event_sha256、打开产出核对
→ ack(accepted | needs_revision) → 计划内还有工作才写第 N+1 轮任务单 → submit
```

停止条件由 C 在启动语里写明：本轮目标达成、给出可核对证据后交 L 验收并停止新增派工；只有计划内确实还有未完成的轮次才继续；验收不通过只开修正轮，不因为“这轮通过”而无限续派。

空闲唤醒是维护者本机另一套机制，没有随包提供。公开的是“C 保持在线”这一种模式：C 的会话在等你给下一句话的时候，通道不会替你叫醒它。没有可用权限或遇到登录、授权提示时，按本机正常流程处理，不能承诺全程无人介入。

## 验证到哪，没验证什么

已在维护者的 Windows 机器和 WorkBuddy 5.9.3 上跑通一个无害的两轮案例：第一轮 C 故意留了缺项并判 `needs_revision`，第二轮修正后 `accepted`，两轮都核对了原生运行记录里的实际模型。

没验证：其它软件版本、其它机器、复杂业务轮次、离线唤醒、跨设备协作、长期无人值守。所以这个包不承诺跨版本兼容，也不承诺“配好就不用管”。

## 人工模式怎么跑

L 把 C 的任务单交给独立的 W 会话，再把报告与实际成果交回 C。两个独立会话把执行和检查分开；C 如果自己补做了成果，必须标明是自查，不能把同一次生成当成独立复核。

人工模式不需要任何配置，代价是 L 要中转消息，跨设备时还要自己解决文件传递。它不是自动模式的降级凑合，边缘条件不满足时它就是正确选择。

## 成本目标说到哪

规划和验收留在主力模型上，执行交给当前可用的低成本或免费执行器。对额度紧张的 Plus 用户，长活可以挪到 W 那侧。但 C 的派工、读报告、审阅和返工沟通仍然消耗主力额度，总量是否更省要按实际任务看，本项目没有做额度计量，也不引用任何订阅限额。免费能力随平台和账号当时可用额度变化，不保证某个执行器长期可用。

## 审阅不止一次

自动派工容易让人以为“一轮派完就该结束”，实际不是。初审发现的问题要 W 修订、C 复审，不能凭 W 一句“已修正”放行；交付或发布前还得把关键标准再走一遍，涉及对外内容时隐私与准确性单独看。没有真实改动就写“无需改动”，不虚构优化，也不靠固定次数放行。自动通道减少的是搬运，检查层数和 L 的最终决定都不因此减少。

## 分工不重叠

自动或人工，这条都不变：C 只规划与检查，W 只执行与报告。C 不代 W 生产成果，W 不代 C 判通过、不代 L 做最终验收。

W 不可用时的正确降级是 C 继续规划、诊断和准备任务单，如实报告阻塞，交 L 决定是等 W 还是改分工；未经 L 同意，C 不把本该 W 交付的成果自己做完。若 L 同意由 C 直接执行，成果要标注“C 直接执行”，同时该轮失去独立检查者身份，需要另找检查方或由 L 亲自核对。

## 状态、重复投递与失败

- 每个业务轮次一个唯一请求ID，配一行 nonce。已固定的报告不原地覆盖，修正另开一轮。
- 投递结果不确定时先跑 `status`，用同一个 id 查 `registered`、`definition`、`report_exists`。不换 id 重投。
- `submit` 只在事务提交前失败时能保证不新增行。提交之后写回执失败属于另一种情况：行已经在库里，按状态处理，不要重投。
- 不自动恢复数据库备份。备份是给人核对用的，恢复是高风险操作，需要单独确认。
- 等待要有边界：单轮 30 至 45 分钟，到点存下成果、未完成项和续接位置。
- 请求模型不等于实际执行模型，实际型号以原生运行记录为准。

## 想接自己的适配

若你已有获授权的工具，可以按下面的能力自行适配。这是能力清单，不是某个产品的 API，也不是可以直接运行的命令。

| 能力 | 输入 | 应返回的信息 |
| --- | --- | --- |
| 提交任务 | 目标项目、请求ID、任务单、成果位置、预算 | 是否接收、执行器任务标识 |
| 查询状态 | 同一请求ID或任务标识 | 未接收、排队、执行中、失败或完成 |
| 读取交付 | 任务标识与报告版本 | 固定报告、实际成果位置、可核对证据 |
| 记录审阅 | 报告版本与 C 的检查结论 | 接受本轮或需新轮修正 |

接入前先确认：工具来源、访问范围、账号授权、目标项目是否一致。技能本身不创建工具，也不授予额外权限；用户明确安装并配置了某个通道，才代表他知道这件事会发生。写适配说明时交待清楚支持的产品版本、使用的接口、配置步骤、验证范围、失败恢复方法，示例只用虚构资料，不提交账号凭据、设备路径、真实会话记录或私有运行日志。

不要通过改第三方内部数据库、复用他人凭据或跳过认证来模拟官方接口。本仓库自带的通道之所以可以写本机数据库，是因为它只按守卫后的单次插入处理一条已审阅的表定义，并且需要用户本人完成配置与授权；这个范围不放大成通用许可。
